# Development

How to run memos on your own machine: the viewer alone, the full stack with multiplayer and uploads, phones and
headsets on your network, the checks CI runs, and every test suite. How the parts fit together is in
[architecture.md](./architecture.md).

## Prerequisites

- **Node.js 22.13 or newer**, with npm. `.nvmrc` pins 22.23.2, and `package.json` accepts `^22.13.0 || >=23.4.0`. The
  local upload API keeps its password registry in Node's built-in SQLite, which needs those versions.
- **SpacetimeDB CLI 2.13.0**, for multiplayer, uploads, the library and the live test suites. On macOS or Linux (on
  Windows, use WSL), install it with the official script and check the version:

  ```bash
  curl -sSf https://install.spacetimedb.com | sh
  spacetime --version
  ```

  Keep the CLI at 2.13.0: the module and the web app pin the `spacetimedb` package to 2.13.0, and the client bindings
  are generated by the CLI. SpacetimeDB's [installation guide](https://spacetimedb.com/install) has the details.

- **Python 3.10 or newer** for the vision pipeline and its tests (CI uses 3.12). A few live suites also run `python3`
  with the standard library only.
- Optional: `cloudflared` for a public HTTPS tunnel, `adb` (Android SDK Platform-Tools) for a Quest over USB, and macOS
  with Xcode for the iPhone app and its check programs ([ios.md](./ios.md)).

The npm scripts use POSIX shell syntax such as `${STDB_PORT:-3055}`, so run them from bash or zsh.

## First run

```bash
npm install
LOCAL_HTTP=1 npm run dev
```

Open http://127.0.0.1:5173. Without a `?memory=` parameter the viewer loads the built-in demo,
`apps/web/public/demo/memory.json`: a synthetic six-second scene with a splat floor generated in code, a ball and a
can. It needs no network and no server besides the dev server. Pause, drag an object and let go, then press Play: the
throw becomes a new take. **Original** in the take picker returns to the untouched recording.

Without SpacetimeDB the viewer is a solo session. The party panel keeps retrying ("Can't reach the multiplayer
server — retrying in N s"), and the terminal logs `ws proxy error` and `http proxy error` lines for `/stdb` and `/api`
until those services run.

`LOCAL_HTTP=1` serves plain HTTP on 127.0.0.1 only. Plain `npm run dev` serves HTTPS with a self-signed certificate on
every network interface, for opening the laptop's address from a phone or headset (see
[Phones and headsets](#phones-and-headsets)).

Pages on the dev server:

- `/`: the viewer. `/?memory=<manifest URL>` opens another scene: URL-encode it; the scene's asset URLs resolve relative
  to the manifest, and its host must allow CORS. `/?memory=/mock/memory.json` shows Spark's public butterfly splat,
  loaded from sparkjs.dev (needs internet). All URL parameters are in [viewer.md](./viewer.md).
- `/<CODE>`: a party, by its seven-character code. Opening or reloading the address rejoins it.
- `/upload`: the viewer with its upload panel open.
- `/library.html`: the memory library.
- `/capture.html`: the capture test page ([capture-testing.md](./capture-testing.md)).
- `/scenes/index.html`: the local pipeline scenes ([Local test scenes](#local-test-scenes)).

The dev server answers unknown paths with the viewer, because party codes live at `/CODE`. Static pages under
`apps/web/public/` therefore need their full path: `/scenes/index.html` works, `/scenes/` opens the viewer.

## The full local stack

Multiplayer and the library need SpacetimeDB; uploads and sign-in also need the upload API. Start them in this order:
the upload API mints its GPU worker identity from SpacetimeDB on its first start.

```bash
# Terminal 1: SpacetimeDB on 127.0.0.1:3055
npm run stdb:start

# Terminal 2: build and publish the module as database memory-replay, then start the upload API on 127.0.0.1:8788
npm run stdb:publish:local
npm run upload:local

# Terminal 3: the web app on http://127.0.0.1:5173
LOCAL_HTTP=1 npm run dev
```

- `stdb:start` is ready when it prints `Starting SpacetimeDB listening on 127.0.0.1:3055`; the line
  `PostgreSQL wire protocol server disabled` is normal. If a server is already running, reuse it. Its data survives
  restarts, so keep its data directory.
- `stdb:publish:local` builds `server/spacetime` and publishes it to the local server as `memory-replay`, the web app's
  default database. It uses your `spacetime login`; without one, publish anonymously
  ([Changing the SpacetimeDB module](#changing-the-spacetimedb-module)).
- `upload:local` runs the upload API (`server/upload/src/node/server.mjs`) with `UPLOAD_STORAGE=local`. Videos and the
  service's state live in `data/uploads/` (git-ignored); keep that folder between runs. `.signing-secret` signs upload
  tickets and encrypts the six-digit password registry, `.accounts.sqlite`; losing it makes the saved passwords
  unreadable. `.worker-identity.json` holds the GPU worker's identity and token; deleting it orphans the uploads already
  assigned to the old worker.
- The dev server proxies `/stdb` (HTTP and WebSocket) to SpacetimeDB and `/api` to the upload API, so the page, a phone
  on your network and a tunnel reach everything through one origin.
- Six-digit password sign-in checks that the account service reports the same SpacetimeDB address as the page uses.
  Through the proxy that address is `http://127.0.0.1:5173/stdb`, so for sign-in start the upload API with
  `ACCOUNT_SERVER_URL=http://127.0.0.1:5173/stdb npm run upload:local`, or use `party:dev` below, which sets it.
  Otherwise sign-in fails with "The account service uses a different database".

To check the stack, open http://127.0.0.1:5173 in two tabs (each tab is its own guest player). In one, open the party
panel with **Solo** at the top, press **Create a party**, then **Copy invite link**, and open the link in the other tab.
Both tabs should list both people; play, pause and seek in the leader's tab reach the other one, and either player can
grab an object while paused. The full party walkthrough is in [multiplayer.md](./multiplayer.md); the upload and
stored-video test on `/capture.html` is in [capture-testing.md](./capture-testing.md).

### One command: party:dev and party:lan

`npm run party:dev` ([scripts/dev/party-dev.mjs](../scripts/dev/party-dev.mjs)) starts the upload API (local storage)
and the web app together, with matching settings, and stops both when either exits. SpacetimeDB still runs on its own,
and the launcher uses its own database, `memory-replay-party`, so publish the module under that name first:

```bash
npm run stdb:start   # terminal 1
spacetime publish -s http://127.0.0.1:3055 --module-path server/spacetime --delete-data=never memory-replay-party
npm run party:dev    # http://127.0.0.1:5173, upload API on 127.0.0.1:8788
```

For both processes it sets `STDB_DATABASE` and `VITE_STDB_DATABASE` (default `memory-replay-party`), `STDB_PORT`
(default 3055), `PUBLIC_ORIGIN` (default `http://127.0.0.1:<VITE_PORT>`), `ACCOUNT_SERVER_URL` (default
`<PUBLIC_ORIGIN>/stdb`, so password sign-in works) and `LOCAL_HTTP=1`. The dev server runs with `--strictPort`, so
the launcher exits instead of moving to another port. If 5173 or 8788 is taken, stop that server or choose free ports:
`VITE_PORT=5180 UPLOAD_PORT=8790 npm run party:dev`. To use the database from `stdb:publish:local` instead, run
`STDB_DATABASE=memory-replay npm run party:dev`.

`npm run party:lan` is the same launcher with `--lan` (or `PARTY_LAN=1`). It picks this machine's private IPv4 address,
listens on every interface, uses `http://<LAN address>:<VITE_PORT>` as the origin and prints it. Open that exact address
on the laptop and on phones on the same Wi-Fi. If the machine has several network interfaces, set
`PUBLIC_ORIGIN=http://<address>:<port>`. This is plain HTTP: guest parties and the 3D viewer work, the rest needs a
secure context ([Same network](#same-network)). `PARTY_HTTPS=1` makes either launcher serve the dev server's self-signed
HTTPS and use an `https://` origin; every device then has to accept the certificate.

### The GPU worker against the local stack

After `upload:local` (or `party:dev`) has started once, `npm run worker:env:local` writes `data/worker.local.env`, a
private (mode 0600) environment for running the pipeline worker on the same machine. It never prints the token.

```bash
npm run worker:env:local
source data/worker.local.env
unset S3_BUCKET MEMREPLAY_UPLOAD_API   # publish into the local scene folder, not to a bucket or API
memreplay worker --once
```

The helper verifies the stored worker token against SpacetimeDB and refuses to overwrite an existing file; pass another
path to write a new one (`npm run worker:env:local -- data/worker-next.env`). Give it the same `PUBLIC_ORIGIN`,
`STDB_*` and `LOCAL_*` settings as the upload API. The worker publishes each scene into
`<LOCAL_SCENE_DIR>/<memoryId>-<requestId>/`, which the upload API serves read-only at `/api/local-scenes/`.

The worker runs every pipeline stage, so it needs a machine set up as in the [pipeline runbook](../pipeline/README.md).
A GPU pod elsewhere can't read a local folder and needs shared S3/R2 storage ([deployment.md](./deployment.md)). Test
uploads (`pipeline: false`: the capture page's simulation and `npm run test:video`) are assigned to their uploader and
never reach a worker.

## Ports and environment variables

The defaults are SpacetimeDB on 3055, the upload API on 8788 and the dev server on 5173. SpacetimeDB avoids 3000 and
3001, which Docker often holds.

These settings come from the shell. The dev server's config ([apps/web/vite.config.ts](../apps/web/vite.config.ts)),
the npm scripts and the upload API read them from the environment, not from `.env` files; only `npm run upload:dev`
loads a file, `server/upload/.env`.

- `STDB_PORT` (3055): the local SpacetimeDB port. `stdb:start`, `stdb:publish:local`, the dev server's `/stdb` proxy,
  `upload:local`, `party:dev`, `worker:env:local` and the live suites' default URL all follow it.
- `STDB_URL`: the `/stdb` proxy target, in place of `http://127.0.0.1:$STDB_PORT`.
- `UPLOAD_PORT` (8788): the upload API's port and the `/api` proxy target. The upload API also reads `PORT`, which wins.
- `UPLOAD_URL`: the `/api` proxy target, in place of `http://127.0.0.1:$UPLOAD_PORT`. It is also the default target of
  `npm run connections:check`.
- `VITE_PORT` (5173): the dev server's port.
- `VITE_HOST`: the dev server's listen address. The default is every interface, or `127.0.0.1` with `LOCAL_HTTP=1`.
- `LOCAL_HTTP=1`: plain HTTP on 127.0.0.1, in place of self-signed HTTPS on every interface.
- `PUBLIC_ORIGIN`: the origin browsers use to open the app. The dev server accepts requests for its hostname besides
  IP addresses, `localhost`, `*.trycloudflare.com` and `*.ngrok-free.app`. `upload:local` builds upload and video URLs
  from it and accepts browser requests from it; its default is `http://127.0.0.1:5173`.
- `UPLOAD_ALLOWED_ORIGINS`: more browser origins the upload API accepts, comma-separated.
- `ACCOUNT_SERVER_URL`: the SpacetimeDB address the account service reports for password sign-in. It must equal the
  page's address (`<app origin>/stdb` through the proxy); it defaults to `STDB_HTTP_URL`.
- `STDB_HTTP_URL` and `STDB_DATABASE`: the server and database the upload API and the worker use. `upload:local`
  defaults to `http://127.0.0.1:$STDB_PORT` and `memory-replay`.
- `UPLOAD_STORAGE`: `local` (set by `upload:local` and `party:dev`) or `s3`, the default. The S3/R2 settings are in
  [server/upload/.env.example](../server/upload/.env.example); copy it to `server/upload/.env` for `npm run upload:dev`.
- `UPLOAD_HOST`: the upload API's listen address: `127.0.0.1`, or `0.0.0.0` when `NODE_ENV=production`.
- `LOCAL_UPLOAD_DIR` (`data/uploads`) and `LOCAL_SCENE_DIR` (`<LOCAL_UPLOAD_DIR>/memories`): the local storage folders.
- `PARTY_LAN=1` and `PARTY_HTTPS=1`: `party:dev` options ([above](#one-command-partydev-and-partylan)).

The settings of individual test suites (`STDB_WS_URL`, `SPACETIME_BIN`, `PYTHON`, `APP_ORIGIN`, `UPLOAD_TEST_R2`,
`UPLOAD_TEST_WORKER_DIR`) are listed with the [test suites](#test-suites).

The `VITE_*` browser settings are compiled into the page, so never put credentials or tokens in them. Set them in the
shell or in `apps/web/.env.local` (git-ignored; start from [apps/web/.env.example](../apps/web/.env.example)):

- `VITE_STDB_URL`: the SpacetimeDB WebSocket URL. The default is the page's own `/stdb/` (`ws://` or `wss://` to match
  the page). A URL with a path must end in `/`.
- `VITE_STDB_DATABASE` (`memory-replay`): the database name.
- `VITE_UPLOAD_API`: the upload API's origin. The default is the page's own `/api`.
- `VITE_ASSET_ORIGIN_ALIASES`: comma-separated former origins of this app whose assets now live at its current origin,
  for after a hostname change.

The hosted site's values are in `apps/web/.env.hosted`, which `vite build --mode hosted` reads
([deployment.md](./deployment.md)).

## Phones and headsets

On a phone or headset, `127.0.0.1` is the device itself, so other devices need the laptop's network address, a USB
forward or a tunnel. WebXR, the clipboard, Web Locks and the capture page's recording and file hashing need a secure
context: HTTPS, or `localhost`.

### Quest over USB

One-time setup: turn on Developer Mode for the headset in the Meta Horizon phone app (this needs a Meta developer
account with an organization), install `adb` (on macOS, `brew install android-platform-tools`), connect the headset with
USB-C and allow USB debugging inside it. Then, every session:

```bash
LOCAL_HTTP=1 npm run dev
adb reverse tcp:5173 tcp:5173
```

In the Quest Browser, open http://localhost:5173 and press **Enter VR**. Over USB, `localhost` counts as a secure
context, so WebXR works without HTTPS. To debug the headset's page, open `chrome://inspect` in desktop Chrome. The
headset's controls are in [viewer.md](./viewer.md).

### Same network

- **HTTPS:** plain `npm run dev` listens on every interface with a self-signed certificate. Open
  `https://<laptop address>:5173` and accept the certificate warning on each device.
- **HTTP:** `LOCAL_HTTP=1 VITE_HOST=0.0.0.0 npm run dev`, or `npm run party:lan` together with the upload API. Plain
  HTTP on a network address is not a secure context: there is no WebXR, the copy buttons can't use the clipboard, the
  capture page can't record or hash files, and without Web Locks a duplicated tab shares its player with the original.
  Guest parties and the 3D viewer work. Send passwords only over HTTPS.

Both devices need the same Wi-Fi, and the laptop's firewall has to allow incoming connections to Node. Venue and guest
networks often isolate devices from each other; a phone hotspot or a tunnel avoids that.

### Public HTTPS tunnel

```bash
npm run dev      # HTTPS on every interface
npm run tunnel   # prints https://<random>.trycloudflare.com
```

With `LOCAL_HTTP=1 npm run dev`, run `cloudflared tunnel --url http://127.0.0.1:5173` instead. The link serves the app,
`/stdb` and `/api` through the dev server's proxy, so nothing else needs exposing, and it is trusted HTTPS for phones
anywhere and for a Quest over Wi-Fi. Anyone with the link reaches your dev server and its local database, so stop the
tunnel after testing.

### Uploads and sign-in from another address

The upload API checks the page's origin, writes it into upload and video URLs, and reports the SpacetimeDB address that
password sign-in compares with the page's. When devices open the app at any address other than
`http://127.0.0.1:5173` (a LAN address, a `.local` name, `http://localhost:5173` on a Quest, a tunnel), pick one
address for every device and start the upload API with it:

```bash
PUBLIC_ORIGIN=https://<random>.trycloudflare.com \
  ACCOUNT_SERVER_URL=https://<random>.trycloudflare.com/stdb npm run upload:local
```

- Requests from another origin get "Origin not allowed" (403); add extra origins with `UPLOAD_ALLOWED_ORIGINS`.
- Stored videos keep the address they were uploaded under: upload again after changing `PUBLIC_ORIGIN`.
- A hostname other than an IP address, `localhost` or a tunnel domain, such as `<name>.local`, also needs
  `PUBLIC_ORIGIN` on the dev server, or Vite answers "Blocked request. This host (…) is not allowed.":
  `PUBLIC_ORIGIN=http://<name>.local:5173 LOCAL_HTTP=1 VITE_HOST=0.0.0.0 npm run dev`.
- **Add to library** resolves a manifest URL against the page, so add library entries from the shared address too, or
  other devices get `127.0.0.1` URLs they can't open.
- `party:dev` and `party:lan` apply these settings for you.

The SceneCaptureDemo iPhone app in the iOS Simulator uses `http://127.0.0.1:5173` by default, so the local stack is all
it needs. A physical iPhone needs one of the addresses above ([ios.md](./ios.md)).

## Changing the SpacetimeDB module

The module is in `server/spacetime/`: tables in `src/schema.ts`, reducers in `src/reducers/*.ts`, shared helpers in
`src/helpers.ts`, and the entry point `src/index.ts`, which exports only the schema and the reducers. After a change:

```bash
npm run stdb:publish:local   # build and republish to the local server; compatible changes keep existing rows
npm run stdb:generate        # regenerate apps/web/src/module_bindings/ from the module
npm run typecheck            # publishing bundles the module without type-checking it
npm test                     # includes the module's tests on SpacetimeDB's test harness
```

Then run the live suites against the republished database: `npm run test:integration`, `npm run test:party` and
`npm run test:adapter` ([Test suites](#test-suites)). `npm run stdb:build` builds the module without publishing it.

- Never edit `apps/web/src/module_bindings/`. Regenerate it with SpacetimeDB CLI 2.13.0 and commit it together with the
  module change.
- Module code must be deterministic: no `Math.random()` or `Date.now()`; use `ctx.random` and `ctx.timestamp`. Reject
  bad input with the `fail()` helper, which throws a `SenderError`, so clients see a readable reason.
- Names differ by side: snake_case on the wire and in SQL (`create_room`, `object_state`), camelCase in TypeScript
  (`conn.reducers.createRoom({...})`, `conn.db.objectState`).
- The `spacetime` CLI defaults to Maincloud. Pass `-s http://127.0.0.1:<port>` for local work; the npm scripts do.
- Check SpacetimeDB's migration rules before changing an existing table. Never delete a shared database to get past a
  failed publish.
- A publish rejected with 403 means the database belongs to another identity. Publish with the CLI login that owns it,
  or under a new name.
- Without a CLI login, publish a throwaway database:
  `spacetime publish -s http://127.0.0.1:3055 --module-path server/spacetime --anonymous <name>`. Each anonymous
  publish uses a new identity, so that database can't be updated later: republish under a new name, and point
  `VITE_STDB_DATABASE` and `STDB_DATABASE` at it.

## Checks

CI ([.github/workflows/ci.yml](../.github/workflows/ci.yml)) runs these on every pull request; run them before you open
one:

```bash
npm run format:check   # Prettier; `npm run format` rewrites the files
npm run lint           # ESLint
npm run typecheck      # every workspace, and tests/
npm test               # Vitest: every package's unit tests and tests/*.test.ts
npm run build          # type-check and build the web app into apps/web/dist
```

For the pipeline:

```bash
pip install -e "pipeline[dev]"   # the memreplay package, pytest and ruff
ruff check .
ruff format --check .            # `ruff format .` rewrites the files
pytest pipeline
```

`npm test` and `pytest pipeline` need no running services, GPU or cloud account. `npm run preview -w apps/web` serves
the production build on port 4173 with the same proxies (HTTPS unless `LOCAL_HTTP=1`).

## Test suites

### Unit tests

`npm test` runs four Vitest projects. Run one with `npm test -- --project <name>`.

- `web` (`apps/web/tests/`): the engine (tracks, the timeline and takes, replay, physics with real Rapier), camera
  modes, desktop, phone and VR input, the VR panel, the party panel, the library, scene bundles, recorded uploads and
  account keys. Runs in Node.
- `spacetime` (`server/spacetime/tests/`): the module's reducers on SpacetimeDB's module test harness.
- `upload` (`server/upload/tests/`): the upload API's routes, local storage, passwords, scene hosting, the connections
  report and the Cloudflare Worker.
- `integration` (`tests/*.test.ts`): cross-package tests that run the real module with web or upload code, such as the
  network adapter on an in-process room. [tests/room-harness.ts](../tests/room-harness.ts) is that room, reusable for
  other client tests.

`pytest pipeline` (`pipeline/tests/`) runs S3–S7 on a synthetic ViPE output with known answers, the worker's
standard-library helpers and the hosted publisher.

### Live suites against your local SpacetimeDB

Start SpacetimeDB and publish the module first. These suites read `STDB_DATABASE` (default `memory-replay`) and
`STDB_WS_URL` (default `ws://127.0.0.1:$STDB_PORT`), and leave their test rows in that database, so point them at a
test database rather than one you care about.

- `npm run test:integration` (`tests/integration/multiplayer.ts`): real WebSocket clients: presence, the shared clock,
  competing grabs, sync after a release, late-join trajectories, disconnect and reconnect, automatic transport recovery,
  an authenticated upload and the worker's HTTP status calls.
- `npm run test:party` (`tests/integration/party.ts`): party rules with four connections (leader, guest, late visitor
  and worker): invite codes, leader-only time, rejected guest writes, the worker's status rights and the ready-scene
  switch, leader transfer and election after a disconnect.
- `npm run test:adapter` (`tests/integration/adapter.ts`): two viewers with their network adapters and a late joiner: a
  throw, a re-grab into a new take, and identical tracks on all three.
- `STDB_DATABASE=<test database> node tests/integration/phone-account.mjs`: the account API's registration, password
  reuse, fixed names and identity/token mismatch. It requires an explicit database and always uses
  `http://127.0.0.1:3055`, whatever `STDB_PORT` says.

### Self-contained suites

These start their own loopback SpacetimeDB with an in-memory database, publish the module, and clean up afterwards;
nothing needs to be running. They need the `spacetime` CLI on `PATH`, or its path in `SPACETIME_BIN`.

- `npm run test:connections` (`tests/integration/connections.ts`, with `connection_worker.py`): the I3, I4, I5 and I7
  contracts. A verified upload creates one `uploaded` memory; the real Python worker polls only its own jobs, downloads
  the exact bytes and publishes a synthetic scene; a waiting party switches to it; two WebSocket clients share a party;
  and `worker:env:local` writes a private environment file. Needs `python3` (or `PYTHON`).
  `npm run test:connections -- --full` also runs the multiplayer and party suites against the same temporary database.
- `npm run test:upload-api` (`tests/integration/upload-api.ts`): the Node upload API with local storage: accounts and
  six-digit passwords before and after a restart, an upload of `tests/fixtures/plant.mp4` with identical bytes back,
  one row on repeated completion, a live viewer subscription and isolation between accounts.
  `UPLOAD_TEST_R2=1 npm run test:upload-api` runs the Cloudflare Worker instead, in `wrangler dev --local` with local
  R2 (`server/upload/deploy/cloudflare/wrangler.jsonc`), and adds the GPU worker bridge: the Python publisher's 91 MiB
  multipart asset and the `ready` status over WebSocket (needs `python3`). `UPLOAD_TEST_WORKER_DIR=<hosting checkout>`
  uses that checkout's built Worker ([deployment.md](./deployment.md)).

### Against the full local stack

With SpacetimeDB and the module, `upload:local` and the web app running:

- `npm run test:video -- <clip> <seconds>` (`tests/integration/video.ts`): uploads a real clip through the app's `/api`
  as a test upload (`pipeline: false`), finds its row with an independent query, downloads it and compares the SHA-256,
  repeats the completion, and prints a `/capture.html?request=…` link to watch it. `APP_ORIGIN` (default
  `http://127.0.0.1:5173`) points it at another address. `tests/fixtures/plant.mp4` is a small non-private clip of about
  9 s: `npm run test:video -- tests/fixtures/plant.mp4 9`.
- `npm run connections:check -- <upload API URL>` (`scripts/dev/check-connections.mjs`): not a test but a read-only
  report from a running upload API (default `UPLOAD_URL`, or `http://127.0.0.1:8788`). It checks the expected tables
  over SQL, prints the configured I3, I4, I5 and I7 endpoints, and exits with 1 when a read fails. It writes nothing,
  and it can't prove bucket permissions, CORS or a running worker.

### macOS with Xcode

These compile the iPhone app's real Swift sources in `apps/ios/SceneCapture/` with `xcrun swiftc`.

- `npm run test:pipeline` (`tests/integration/ios-pipeline.mjs`): compiles `apps/ios/Tests/PipelineUploadChecks.swift`
  with the app's upload queue and runs the upload API suite with `UPLOAD_TEST_R2=1`. The native queue recovers a lost
  completion, an expired receipt and a restart without a duplicate; the real Python worker loop downloads the exact clip
  and marks it `ready` (GPU stages substituted); a failed stage reports `failed`.
- `node tests/integration/ios-password.mjs`: compiles `apps/ios/Tests/PasswordSignInChecks.swift` and checks the app's
  six-digit sign-in and copy-password paths against a local stub API, including refreshed server capabilities and a
  server without six-digit passwords.
- `apps/ios/Tests/ContractChecks.swift`, offline: encodes real files and checks the capture requirements (24, 25 and
  30 fps with audio pass; silent, 15 fps and low-resolution files fail) and the browser-compatible account key format:

  ```bash
  xcrun swiftc -parse-as-library apps/ios/SceneCapture/AccountKey.swift apps/ios/SceneCapture/Recorder.swift \
    apps/ios/SceneCapture/CaptureRequirements.swift apps/ios/Tests/ContractChecks.swift -o /tmp/memos-native-checks
  /tmp/memos-native-checks
  ```

- `npm run ios:demo:build`: builds the SceneCaptureDemo app for the iOS Simulator.

### Against deployed services

The suites in `tests/e2e/` default to the hosted site's settings in `apps/web/.env.hosted`. They leave labelled test
accounts and memories on the service they test.

- `npx tsx tests/e2e/upload-public.ts https://<upload API origin>`: a real upload of `tests/fixtures/plant.mp4` to a
  deployed upload API, which must use the hosted site's database: account creation and restore, an upload with
  processing off, duplicate prevention, the exact bytes and a range request back, and the same row over the WebSocket.
  It keeps its resumable test account in `data/public-upload-test.private.json` (mode 0600) and writes
  `data/public-upload-verification.json`.
- `npm run test:pipeline:live -- --clip /absolute/clip.mp4 [--api https://<upload API origin>] [--timeout-seconds 7200]`
  (`tests/e2e/pipeline-live.ts`, macOS with Xcode): the real acceptance test. A new test account uploads the clip
  through the native queue, a running GPU worker processes it, and the suite waits (two hours by default) for `ready`
  in both the API and a WebSocket subscription. It then validates `memory.json` with `validateManifest`, requires a
  non-empty background splat, and fetches every referenced asset. Nothing is substituted. The API defaults to
  `VITE_UPLOAD_API` in `apps/web/.env.hosted`. The evidence goes to `data/pipeline-acceptance-<timestamp>/`:
  `result.json`, and `account.json` (mode 0600), which holds the test account's password, so keep it private.
- `apps/ios/Tests/HostedUploadChecks.swift` (macOS): with `--live`, creates a synthetic test account and a tiny
  generated clip on the hosted upload API (its origin is set in the file), uploads the clip with processing off and
  compares the downloaded bytes:

  ```bash
  xcrun swiftc -parse-as-library apps/ios/SceneCapture/AccountKey.swift apps/ios/SceneCapture/Recorder.swift \
    apps/ios/Tests/HostedUploadChecks.swift -o /tmp/memos-hosted-checks
  /tmp/memos-hosted-checks --live
  ```

## Local test scenes

### Public splat test

```bash
node scripts/dev/setup-splat-test.mjs
LOCAL_HTTP=1 npm run dev
```

The script downloads Spark's public butterfly sample (`https://sparkjs.dev/assets/splats/butterfly.spz`, checked
against a pinned SHA-256), generates a small floor and writes three manifests into `apps/web/public/splat-test/`
(git-ignored). Rerunning it reuses the downloaded sample.

- `/?memory=/splat-test/rendering.json`: one stationary splat (178,093 splats with the floor).
- `/?memory=/splat-test/two-splats.json`: two copies (355,225 splats).
- `/?memory=/splat-test/interaction.json`: a grabbable copy: pause, drag, release and replay a take.

These test the renderer and interaction with a public asset; they aren't team footage and say nothing about the
pipeline. The sample's publisher and credits are at [sparkjsdev/assets](https://github.com/sparkjsdev/assets); no asset
license is implied by the renderer's code license, and the sample is never committed.

### Pipeline scenes

Scenes from the vision pipeline open from `apps/web/public/memories/<id>/` (git-ignored). Copy a published scene folder
there, for example with `memreplay publish <work dir> --to apps/web/public/memories/<id>`, or from the GPU pod with
`bash pipeline/runpod/pull.sh <id>` (SSH settings: `pipeline/runpod/ssh.env.example`). Keep each folder intact:
`memory.json` refers to its assets by relative paths. Then index the folder:

```bash
python pipeline/tools/index_scenes.py
```

This writes `apps/web/public/memories/index.json`. `/scenes/index.html` lists the indexed scenes, with links to the
dynamic and static versions in free and guided mode, and dev seeding (below) reads the same index. To open one
directly, use `/?memory=/memories/<id>/memory.json`, or `memory.static.json` for the room alone. A `preview.jpg` next to
`memory.json` is the scene's card image; `node pipeline/tools/preview.js [id ...]` renders it (it needs `puppeteer-core`
from `pipeline/tools/package.json`, Chrome at `CHROME`, and a dev server at `CAPTURE_URL`, default
`http://127.0.0.1:5177`).

To try the browser importer, package a scene folder with
`python pipeline/tools/package_scene.py <scene folder> <name>.memos.zip` and import it on `/library.html#import-scene`
([scene-format.md](./scene-format.md)).

`npm run build` copies everything in `apps/web/public/` into `apps/web/dist`, including the git-ignored `memories/`,
`splat-test/` and `local/` folders. Don't publish that output while private scenes are in it; the hosted build
(`scripts/deploy/build-hosted-web.mjs`) copies only `demo/` and `mock/`.

### Loading local scenes into a library

On the dev server, with SpacetimeDB running, the library's empty state and the viewer's party panel (under **Add a
memory**) offer **Load local memories (N)**. It registers every indexed scene as a ready memory of the current account
or guest, skipping scenes already in the library. `?seed=local` on `/library.html` or on the viewer does the same once,
after connecting. The registered URLs use the page's origin, so seed from the address other devices will use. The code
is [apps/web/src/library/dev-seed.ts](../apps/web/src/library/dev-seed.ts); nothing of it runs in a production build.

## Debugging

- `window.__memreplay` (dev server only): the viewer, the party session, the loaded memory, the scene, camera, renderer,
  controls, the follow-mode path follower and the network adapter, plus `positionsAt(t)` (every object's position at
  time `t`, for comparing tabs of one party) and `takes()` (every take with its recorded frame counts).
- `window.memoryReplay` is the running viewer in every build, and the page dispatches a `memoryreplay:ready` event
  (`detail` is the viewer) once a memory is loaded. `window.__memreplayScene` exposes the scene, camera and renderer for
  scripted screenshots.
- `window.__vrlog` (dev server only) keeps the last 300 headset input events, to read over `chrome://inspect` after a
  Quest session.
- `?stats` shows the playback state and frame rate. `?lod=0` draws every splat (slower; for render comparisons).
  `?xrPreview` (dev server only) shows the in-headset panel on the desktop, worked with the mouse; it isn't a headset
  emulator.
- To read the database, query it with SQL. A test upload has `pipeline_identity` equal to `owner`:

  ```bash
  spacetime sql -s http://127.0.0.1:3055 memory-replay \
    'SELECT id, title, owner, pipeline_identity, status, source_url FROM memory'
  ```

- `GET /api/health` only says that the upload API is running; `npm run connections:check` checks its database reads.

## Troubleshooting

- **A port is already in use.** Reuse the running server or stop it; don't start a second one. `STDB_PORT` moves
  SpacetimeDB for every script, the proxy and `upload:local` at once. When 5173 is taken, `npm run dev` says the port
  is in use and moves to the next free one, and `PUBLIC_ORIGIN`, the tunnel and `adb reverse` then point at the wrong
  port: free it, or set `VITE_PORT` and use that port everywhere.
- **"Can't reach the multiplayer server — retrying in N s".** SpacetimeDB isn't running on the port the dev server
  proxies to (`STDB_PORT` or `STDB_URL`), or the page's database (`VITE_STDB_DATABASE`, default `memory-replay`) hasn't
  been published there.
- **`/api` requests fail with HTTP 500 and `http proxy error` in the terminal.** The upload API isn't running on
  `UPLOAD_PORT` (8788): start `npm run upload:local`.
- **"Origin not allowed" (403).** The page's origin isn't `PUBLIC_ORIGIN` (default `http://127.0.0.1:5173`; note that
  `localhost` is a different origin) or in `UPLOAD_ALLOWED_ORIGINS`. Restart the upload API with the address the browser
  uses ([Uploads and sign-in from another address](#uploads-and-sign-in-from-another-address)).
- **"The account service uses a different database" on sign-in.** Set `ACCOUNT_SERVER_URL=<app origin>/stdb` and the
  page's `STDB_DATABASE` for the upload API, or use `npm run party:dev`.
- **"Blocked request. This host (…) is not allowed."** Set `PUBLIC_ORIGIN` for the dev server to the address you open.
- **A phone or headset can't reach the laptop.** Check that both are on the same Wi-Fi, that you use the laptop's
  address (`127.0.0.1` on a phone is the phone), and that the firewall allows incoming connections to Node. Some
  networks isolate devices; use a hotspot or a tunnel. For a Quest over USB, run `adb reverse tcp:5173 tcp:5173` again
  in each session.
- **A recording or library entry plays only on the laptop.** It was saved with a `127.0.0.1` URL. Upload or add it again
  from the shared address.
- **Two tabs act as one player.** A duplicated tab copies the original's session. On secure origins, Web Locks give the
  copy a new guest identity; plain-HTTP network addresses have no Web Locks, so open a fresh tab or another browser.
- **An upload stays `uploaded`.** That is expected until a worker processes it, and test uploads (`pipeline: false`)
  stay `uploaded` even with one.
- **`npm install` times out.** Some venue networks throttle the npm registry; try another network, such as a phone
  hotspot.

## Limits of local testing

- Nothing in the local stack or the test suites runs GPU reconstruction: the isolated suites publish synthetic scenes,
  and uploads stay `uploaded` until a configured worker processes them.
- No suite runs on a real Quest, phone or glasses. Desktop rendering speed says nothing about a headset's frame rate.
- One player per tab relies on Web Locks, which plain-HTTP network addresses don't have.
- Uploads over 100 MB through a quick tunnel are untested; Cloudflare may cap request bodies at that size.
- The viewer bundle is about 7.8 MB (2.8 MB gzipped), almost all Spark and Rapier, which load before anything renders,
  so `npm run build` prints Vite's large-chunk warning. Measure the first load on the network you will present on.
