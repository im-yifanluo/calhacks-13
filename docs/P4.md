# P4: multiplayer, phone controls, and upload

This branch implements Jerry's P4 lane. A custom native phone app is **not required for this import workflow**: use Meta AI to import glasses recordings to the phone, then select the video in this web app. An optional native iPhone app now adds live glasses preview, O/F recording and automatic upload. See the [capture test guide](CAPTURE_TEST.md) for setup, exact-file/database checks and the native build/device verification limits.

## What runs here

| Part             | Behavior                                                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| SpacetimeDB 2.13 | Memories and processing status, rooms/codes, presence, poses, shared playhead, branch ancestry, exclusive object ownership, recorded trajectories |
| Phone/web        | Orbit and pinch zoom, walk joystick, pause then drag to grab, flick to throw, room links, branch selection, video upload/progress/cancel/retry    |
| Upload service   | Authenticated presigned S3/R2 PUT; verifies uploaded object size/type before registering a memory; credentials stay on the server                 |
| iPhone capture   | Native Meta DAT preview; O records, F stops/finalizes/uploads; persistent retry queue and stored-video playback                                   |
| Capture test     | `/capture.html` shows real database rows, file reachability/hash and stored-video playback; local disk storage needs no cloud account             |
| Worker handoff   | An uploaded memory contains its video URL and assigned worker identity; Python helper reports processing/ready/failed over authenticated HTTP     |
| Local demo       | Explicit `?demo=1` uses debug geometry and a floor, with real database sync and Rapier simulation                                                 |

P1/P2 still own reconstruction, job execution, storage provisioning and real assets. P3 still owns production object GLB/splat loading, environment colliders, Quest controller/hand grabbing, avatar hands and final timeline UX. The existing WebXR entry point and background splat path remain available; this branch is not a finished glasses-to-reconstruction system. The TypeScript/Python `memory.json` contract is unchanged.

## Run without cloud credentials

Use Node **22.12+**, npm, and the **SpacetimeDB CLI 2.13.0**. Install the CLI from [SpacetimeDB's official installation guide](https://spacetimedb.com/install). Keep CLI, module and browser SDK versions aligned.

```bash
npm ci
npm run typecheck
npm test
npm run build
```

Start a local database in a separate terminal:

```bash
spacetime start --listen-addr 127.0.0.1:3000
```

Publish and launch the app:

```bash
npm run stdb:publish:local
LOCAL_HTTP=1 npm run dev
```

The publish command uses your CLI login and creates/updates `memory-replay` on the local server. For a disposable test without a CLI login, publish once with `spacetime publish --module-path server/spacetime --server local --anonymous memory-replay`. Anonymous publication uses a new identity each time, so subsequent updates to that database will not have ownership; use a fresh name and set `VITE_STDB_DATABASE` and `STDB_DATABASE` consistently, or log in and publish a database owned by that CLI identity. Do not clear an existing database to solve an ownership error.

Open **http://127.0.0.1:5173/?demo=1**. This explicit local HTTP mode binds to loopback and avoids certificate setup for desktop QA. Default `npm run dev` uses HTTPS. Use a trusted HTTPS deployment or tunnel for phone/Quest testing.

1. Expand **Load a finished memory**, leave the URL field blank and click **Add to library**.
2. Under **Your room**, enter a name, select the ready mock memory and click **Create room**.
3. Copy the room link into a second independent browser tab/device. Session identity is per tab; a reload of that tab retains its identity. Some browsers copy session storage when duplicating a tab, so use a fresh tab or separate browser if both show one identity.
4. Check that both show two people. Pause, seek to about 1 second, and drag the cube. The first edit creates a branch automatically. Release to throw. The other client sees the motion.
5. Wait until it settles, seek back to the branch start, then play. Both clients replay the saved trajectory. Choose **Original** to return to the captured track.
6. A later grab of the same resting object forks a child, preserving the earlier recording. Use **Fork** explicitly for other alternate edits. Seeking/changing branches is rejected while a simulation still owns an object.

Run the real network suite against that disposable database:

```bash
npm run test:integration
# For a differently named local database:
STDB_DATABASE=my-test-db npm run test:integration
```

It creates labeled test memories/rooms. It exercises actual WebSockets, presence, pose sync, shared pause, competing grabs, movement after release, late-join keyframes, disconnect cleanup, identity reconnection, automatic transport recovery, authenticated HTTP status updates, and an upload handler using local fixture bytes/storage. This validates the service/database handoff; the test's four-byte payload is a transport fixture, not a decodable video or a reconstruction.

`npm test` runs 14 tests including the official SpacetimeDB module harness, receipt tampering/expiry, HTTP origin/auth/metadata validation, repeated upload completion, branch isolation, and flick velocity. No R2/S3 account or GPU is used. Run `npm run upload:local` alongside the database and HTTP app to upload real video to local disk and register it in SpacetimeDB. Open `/capture.html` to verify the row and play the stored file. Follow the [capture test guide](CAPTURE_TEST.md) for LAN/iPhone settings. The cloud upload option is below; neither transport simulates reconstruction.

## Configure a real upload

```bash
cp server/upload/.env.example server/upload/.env
```

Fill that ignored file locally. Do not commit it or put secrets in `VITE_*` variables.

- `STDB_HTTP_URL` and `STDB_DATABASE`: the same server/database used by the browser.
- `PIPELINE_IDENTITY`: the stable worker's 64-character identity, without `0x`. The worker keeps its matching `PIPELINE_TOKEN` on its own host. The upload service needs only its identity, not its token.
- `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`: bucket and endpoint. R2 normally uses its account endpoint and region `auto`; AWS S3 uses the actual region and can omit the endpoint.
- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`: credentials with PutObject/GetObject metadata permissions for the upload prefix. The pipeline needs separate asset-write access.
- `ASSET_BASE_URL`: stable asset URL accessible to the worker and viewers. This demo stores readable URLs in public tables. Use a bucket/CDN designated for shareable demo assets.
- `UPLOAD_SIGNING_SECRET`: random secret of at least 32 characters, retained across service restarts so upload receipts remain valid.
- `UPLOAD_ALLOWED_ORIGINS`: exact comma-separated browser origins, including the current phone/Quest HTTPS URL.

```bash
npm run upload:dev
```

The service binds to `127.0.0.1:8788`; Vite proxies `/api`. The browser puts the video directly to object storage. Presigned URLs expire after 15 minutes; completion receipts expire after an hour. Failed completion can be retried with the same file and title in the same tab, without uploading again while the receipt remains valid.

Set bucket CORS to allow `PUT`, `GET`, and `HEAD` from the app's HTTPS origin, allow `Content-Type` and any required signed headers, and expose `ETag`. Serve manifests, tracks, `.spz`, and `.glb` with readable CORS headers. Update both CORS and the upload origin allowlist when a temporary tunnel URL changes.

The signing service verifies the user's SpacetimeDB token with `/v1/identity/<identity>/verify`. Completion checks object size and type via HEAD, then calls `create_memory` with the user's bearer token. The request ID makes completion idempotent even after a worker has marked the memory ready. This validates transport metadata, not the contents of a video; P1's ingest must decode/validate it.

For deployment, serve `apps/web/dist` with SPA fallback (including `/upload`) and proxy both **HTTP and WebSocket** traffic under `/stdb/` to SpacetimeDB, and `/api` to the upload service. The HTTP path is required for the SDK's short-lived WebSocket token exchange. Alternatively set `VITE_STDB_URL` to the full server root and `VITE_UPLOAD_API` to the upload origin before building. A path-based `VITE_STDB_URL` must end in `/`.

## P1/P2 worker contract

Subscribe to the public `memory` table and take rows with `status === 'uploaded'` assigned to your worker identity. `sourceUrl` is the uploaded clip, `id` identifies the job, and `durationUs` is browser-reported duration. Use one worker/queue to avoid processing the same row concurrently; this branch does not provision a Runpod worker or job scheduler.

After fetching the clip, report status from the worker environment:

```bash
# Provide STDB_HTTP_URL, STDB_DATABASE, PIPELINE_TOKEN in the worker environment.
python3 scripts/pipeline-status.py 123 processing --progress 0.1
python3 scripts/pipeline-status.py 123 processing --progress 0.7
python3 scripts/pipeline-status.py 123 ready --progress 1 --manifest-url https://assets.example.com/memories/123/memory.json
# On failure:
python3 scripts/pipeline-status.py 123 failed --progress 0.7 --error 'Pose estimation failed'
```

Replace `123` and the URL with the actual row and exported manifest. Allowed transitions are uploaded → processing/failed; processing → processing/ready/failed; failed → processing; ready → ready. Processing progress is monotonic until a failed job is retried. Ready requires a manifest URL and progress 1. Only the assigned worker identity may update the row; the browser sees updates through subscriptions. There is no simulated worker in the normal app.

## P3 integration contract

Use `Multiplayer` from `apps/web/src/net/index.ts` and the generated `module_bindings`.

- `net.time()` derives the shared media time from server anchors, with clock offset calibrated through round trips. State writes happen on pause/seek, not every render frame.
- `net.grab(objectId, pose)` is an awaited authority request. Move only after success. Poses use meters, +Y up, normalized XYZW quaternions and linear velocity in meters/second.
- The server distinguishes `heldBy` from `simOwner`. Release with `rest: false` clears the hand but preserves simulation ownership. Stream `moveObject` at about 15 Hz until sleep.
- Save ordered, non-overlapping `saveBranchKeyframes` chunks **before** releasing with `rest: true`. Each chunk contains at most 120 `{t,p,q}` samples, times in media seconds, and `startMediaUs` equal to the first sample's rounded microseconds. The demo adapter flushes at 25 samples.
- Use `branchFrames` to resolve parent trajectories only up to the child's fork, then interpolate. Untouched objects still use original tracks. Late joiners subscribe to recorded chunks.
- The phone `TouchInput` uses pointer events so mouse and touch share one path. `PhysicsBridge` supplies minimal local floor/box/sphere/capsule simulation for P4 testing; replace or extend it with P3's production physics and colliders. Convex visuals/colliders in this adapter are explicit cube fallbacks.
- Head and hand positions are sent at 12.5 Hz; the demo renders remote heads. P3 can render hands/controllers from the same player rows.
- Regenerate bindings with `npm run stdb:generate` after changing the module schema. Run `npm run typecheck` explicitly: the CLI bundler may not find a workspace-hoisted `tsc` even when it successfully bundles.

Branches and writes are room-scoped; reads are currently public and the demo subscribes to all public tables. Room codes are invitations for a shared hackathon demo, not an access-control boundary. Production private memories need scoped subscriptions/views, asset authorization, quotas and a trusted worker/object registry. Disconnect clears object ownership after the last connection for an identity closes; an interrupted trajectory can contain only samples already saved.

## Ray-Ban Wayfarer and Quest test

1. Pair your existing Wayfarer glasses with Meta AI. Confirm the generation and available media settings in the app: **Wayfarer is the frame style, not a guarantee of 3K**. Gen 2 supports 3K; choose 30 fps and the maximum available resolution. If the app exposes stabilization controls for that mode, use the setting agreed with P1; do not assume an OFF control exists on every generation/firmware. [Meta's Gen 2 announcement](https://about.fb.com/news/2025/09/ray-ban-meta-gen-2-better-battery-life-video-capture/) and [Ray-Ban specifications](https://www.ray-ban.com/usa/l/discover-ray-ban-meta-ai-glasses).
2. Record a short, well-lit scene with a textured background and one slow rigid object. Keep head turns slow. Capture a separate static sweep for P1. Start with 10–20 seconds to shorten the first processing test.
3. Import captures through Meta AI and save/select the recording in the phone's camera roll/gallery. Check that it plays there. The exact import/save controls depend on the app version; follow [Ray-Ban's official import/export FAQ](https://www.ray-ban.com/usa/c/frequently-asked-questions-ray-ban-meta-smart-glasses).
4. For capture/database verification alone, follow [CAPTURE_TEST.md](CAPTURE_TEST.md); no worker is needed. For reconstruction, with storage/service/worker configured, open the trusted HTTPS app URL on the phone, then `/upload`. Enter a title, select the exported MP4/MOV, and upload. If metadata cannot be read, export an H.264 MP4 copy. Expect uploaded → processing → ready as the real worker progresses; do not mark the mock scene as a reconstruction of this video.
5. Create a room for the ready memory. Open the same room link in Quest Browser, then enter VR. Check head presence and shared pause/seek with the phone. Quest hand/controller grabbing and production scene quality are P3's device acceptance checks.
6. On the phone, pause, grab, release, wait for rest, rewind and compare both displays. Reopen the room in a fresh browser to verify the saved branch. Test interruption/reconnection and ensure ownership is released after a participant leaves.

For phone/Quest access during local development, run `LOCAL_HTTP=1 npm run dev`, then deliberately expose that development app with `cloudflared tunnel --url http://127.0.0.1:5173`. Use the resulting trusted HTTPS origin, and configure CORS/origins before uploading. Keep only intended demo data in that database. Stop the tunnel after the test. The current production build is about 7.7 MB of JavaScript (2.8 MB gzip), including the existing Spark/Rapier dependencies; download/startup and headset frame rate need device measurements. No physical glasses, phone or Quest test was performed by this branch's automated checks.
